# Архитектура Коробки

Дата: 8 сентября 2026 года. Статус: проект, конкретные пакеты и механизмы требуют испытаний.

## 1. Компоненты и границы

| Компонент | Назначение | Статус решения |
|---|---|---|
| NanoPi R3S / R3S LTS, FriendlyWrt | Аппаратная и системная база второго экземпляра | Фактические параметры получить обследованием |
| AmneziaWG + tools + LuCI | Независимые исходящие туннели с управлением через LuCI | Целимся в поддержку 3.1; совместимый комплект ещё не выбран |
| Podkop / sing-box | Выбор выхода для трафика и секций, локальный Mixed Proxy | Закрепить и испытать совместимые версии |
| MTG | Telegram MTProto proxy, исходящий upstream через локальный SOCKS | Принято; точный релиз и FakeTLS-параметры проверить |
| Отдельный WireGuard | Входящий доступ телефонов | Принято, не смешивать с исходящими туннелями |
| Небольшая LuCI-панель | Первый запуск, подключения, QR, статусы и обслуживание | Предложенное имя `luci-app-korobka`, ещё не реализована |

Версия AmneziaVPN, версия протокола AWG, версия OpenWrt-пакета и kernel ABI не взаимозаменяемы. Не объявлять сохранённый в корне модуль реализацией 3.1 без проверки. Совпадение строки `uname -r` само по себе недостаточно для произвольного kernel-модуля: проверяются ABI, конфигурация, сборочные источники и зависимости.

Кандидаты из обсуждения: YAAWG (`this-username-has-been-taken/amneziawg-openwrt`) и другие OpenWrt-интеграции AWG. Это направления проверки, не утверждённые поставщики. Предпочтение — согласованному kernel-модулю; Go-реализация рассматривается как техническая альтернатива при проблемах совместимости и после проверки производительности. Релизы и commit нужно повторно проверить непосредственно перед сборкой.

## 2. Топология

Базовый предлагаемый режим:

```text
Интернет / роутер владельца -> WAN коробки -> LAN коробки -> устройства / точка доступа
```

LAN коробки не включать вслепую в существующую сеть с работающим DHCP. Режим дополнительного шлюза в существующей LAN требует отдельной схемы шлюза, DNS и маршрутов; он не объявлен автоматически готовым. Проверять пересечения WAN, домашней сети, VPN-подсетей и адресов импортируемых профилей.

```text
LAN -> Podkop -> исходящий awg_out_N -> сервер из загруженного .conf -> интернет
             -> direct -> WAN, только когда это разрешено политикой

Телефон -> wg_access -> разрешённая LAN
                    -> Podkop -> выбранный исходящий AWG, для режима полного доступа

Telegram -> MTG -> локальный SOCKS секции Podkop -> выбранный AWG -> серверы Telegram
```

Имена интерфейсов условные. Число `awg_out_N` определяется профилями и ресурсами, не фиксируется тремя. Под несколько независимых выходов не складывать несколько конкурирующих default-peers в один интерфейс.

## 3. Маршрутизация и изоляция

Исходящий интернет, входящий доступ телефона и управление — отдельные политики. Сбой исходящего AWG не должен отключать локальную панель или сам входящий канал управления разрешёнными сервисами.

Для интерфейсного сценария Podkop не разрешать импортируемому `0.0.0.0/0` самовольно захватывать системный default route через `Route Allowed IPs`. Сохранять корректные маршруты к endpoint туннелей, прямому WAN и ответы на входящие соединения. Не копировать из рабочей коробки числовые таблицы и marks без инвентаризации конфликтов.

Политики для v1: основной выход, дополнительный/специальный выход, Telegram-выход. Защищённая группа без рабочего назначенного VPN не должна незаметно уходить напрямую. Разрешённый direct-трафик не обязан прекращать работу при отказе VPN. Показать владельцу причину деградации.

Проверять IPv4, IPv6 и DNS. Для непокрытого IPv6 — явная блокировка в соответствующей политике, а не предположение, что он сам не пойдёт через WAN. Bootstrap DNS и время должны позволять поднять стек без циклической зависимости от ещё неработающего туннеля. Конкретный DNS-транспорт выбирается после испытаний.

Предлагается сначала ручное переключение выходов. Автоматический failover — отдельная задача: активные проверки через нужный интерфейс, гистерезис, пауза возврата, ограничение повторных попыток. Наличие автоматического выбора прокси в Podkop не считать подтверждением failover произвольных AWG-интерфейсов.

## 4. MTG и внутренний SOCKS

Согласованная связка:

```text
Telegram-клиент -> MTG на коробке -> SOCKS Mixed Proxy секции Podkop -> AWG этой секции
```

Не нужен второй внешний прокси. MTG и SOCKS находятся на одной коробке. Владелец выбирает Telegram-выход; система связывает MTG с соответствующей секцией. Не править вручную конфигурацию sing-box, которую генерирует Podkop.

Внутренний SOCKS доступен только локальным процессам. Предпочтительна привязка к loopback, если её поддерживает выбранная версия; обязательны ограничения firewall для LAN/WAN/входящего VPN. Не выставлять этот порт вместо MTG.

Проверить фактический upstream, DNS и отсутствие запрещённого прямого fallback. Открытый TCP-порт MTG не означает, что он способен передать трафик. Если локальный SOCKS недоступен, показать ошибку зависимости. FakeTLS, домен маскировки, порт и параметры MTG подготавливаются системой; совместимый набор ещё нужно испытать.

Для v1 один отдельный secret на коробку. Для разных Telegram-пользователей одной коробки QR может содержать одинаковые параметры. Это не отдельная личность каждого клиента и не обещание персонального отзыва. Telegram-ссылка имеет вид:

```text
tg://proxy?server=<доступный-адрес>&port=<порт>&secret=<секрет>
```

QR не создаёт сетевую доступность. Не обещать, что MTProto-прокси заменяет системный VPN или гарантированно обслуживает все типы звонков.

## 5. Входящий WireGuard и публичный адрес

Отдельный WireGuard-интерфейс, peer на каждый телефон, адрес из отдельной VPN-подсети. Это не L2-мост и не выдача телефонам адресов домашним DHCP.

Режимы: разрешённая домашняя сеть либо интернет через коробку. Ограничения реализуются серверным firewall и маршрутами, а не только `AllowedIPs` в редактируемой клиентом конфигурации. Панель/LuCI не открываются через телефонный VPN даже в режиме полного туннеля. Не обходить этот запрет широким masquerade из VPN в LAN.

Никакого скрытого сервисного доступа разработчика, объединения сетей владельцев или общей VPN-идентичности. Обычный WireGuard не считать гарантированно доступным во всех мобильных сетях. Возможный AWG-входящий режим — отдельное расширение, не замена требований v1 без согласования.

Прямой вход через белый IPv4; при вышестоящем роутере требуется разрешённая автоматическая публикация нужных портов. Публиковать только необходимые UDP/TCP, не LuCI/SSH и не общий DMZ. Нет дополнительного VPS/relay. Обнаружение адреса и подтверждение входящей доступности — разные стадии, подробно в [первом запуске](FIRST-BOOT.md).

## 6. Панель и backend

Предлагается LuCI + UCI + rpcd/ubus и небольшой backend с белым списком операций. Не вводить Docker, PostgreSQL и отдельную тяжёлую платформу только ради мастера и QR. В первой версии достаточно роли владельца.

| Раздел | Функции |
|---|---|
| Состояние | WAN, DNS, туннели, выбранные назначения, причины ошибок |
| Подключения | Импорт в любой момент, назначения, тестирование, замена и удаление |
| Телефоны | Добавление peer, выбор прав, повторный QR, экспорт, отзыв |
| Telegram | QR/ссылка, состояние MTG/upstream, перевыпуск общего секрета |
| Обслуживание | Версии, очищенная диагностика, персональный бэкап, проверенные обновления |

Контроль доступа на сетевом и серверном уровнях, не только в браузере. Защита сессии и CSRF; запрет произвольного shell через API; сериализация изменений; сохранение пути управления и откат.

Повторный QR WireGuard предполагает локальное хранение экспортируемого приватного ключа клиента: каталог 0700, файлы 0600, локальная генерация QR, ответ с запретом кэширования, никакого логирования тела. Доступ root к устройству компрометирует сохранённые профили; не описывать права файлов как защиту от root. Одноразовая выдача без хранения — возможный будущий строгий режим, не текущий основной сценарий.

## 7. Сервисы и гонки

Не переносить историческое отключение применения LuCI как обязательную часть продукта. Новая сборка должна переживать Save & Apply, холодный запуск, потерю WAN и переподключение туннелей.

| Владелец слоя | Ответственность |
|---|---|
| netifd/UCI | Конфигурация и жизненный цикл сетевых интерфейсов |
| Podkop | Его правила и генерируемая конфигурация sing-box |
| procd | Надзор за долгоживущими процессами |
| Координатор коробки | Блокировка параллельного применения, готовность зависимостей, ограниченные повторы и диагностика |
| LuCI | Вызов API, не второй независимый конфигуратор тех же файлов |

Локальная панель и входящий WireGuard не зависят от готовности исходящего AWG. Для зависимой цепочки: WAN/маршрут endpoint -> AWG и активная проверка -> Podkop/sing-box -> локальный SOCKS -> MTG. Это логические зависимости; интеграцию с реальными init-скриптами выбранных версий требуется проверить. Не создавать двух независимых владельцев sing-box.

Не полагаться только на фиксированные sleep. Нужны события, проверки готовности, timeout, backoff, блокировка повторного запуска, наблюдаемое состояние degraded. Отказ одного профиля не должен перезапускать без необходимости все остальные.
